### Tables and key invariants

- `users(phone UNIQUE CHECK ~ '^\+9779[0-9]{9}$', role user_role, first_name, last_name?)`.
- `customer_addresses`: Nepal hierarchy + `exact_lat/exact_lng` (double) + `location` **generated**
  `ST_SetSRID(ST_MakePoint(exact_lng, exact_lat), 4326)` with a GiST index. Province 1–7, ward ≥ 1.
- `vendors`: SPEC Vendor fields + `user_id`, `business_name`, `base_delivery_fee_npr`,
  `scheduled_downgrade`, `fulfillment_mode` ∈ {SELF_DELIVERY, PLATFORM_FLEET}. `pricing_model` is
  nullable until LIVE (CHECK). SUBSCRIPTION ⇒ commission 0 (CHECK). `location geometry(Point,4326)`
  with two GiST indexes (geometry, and `(location::geography)` for metre-accurate `ST_DWithin`).
  **Wallet floor:** `CHECK (wallet_balance_npr >= -2000 OR status = 'SUSPENDED')`, plus trigger
  `enforce_vendor_wallet_limit`, which suspends when the balance is strictly below
  `platform_settings.vendor_wallet_suspension_limit_npr` (configurable within [-2000, 0]).
  `wallet_balance_npr` is a **projection**: only ledger postings may change it (guard trigger
  `vendors_a_guard_wallet_projection`).
- `products(vendor_id, name UNIQUE per vendor, price_npr > 0, stock_quantity >= 0, is_active)`.
- `orders`: SPEC OrderSnapshot + `idempotency_key UNIQUE`, `reservation_id UNIQUE`,
  `driver_user_id`, `payment_gateway_ref` (UNIQUE per `payment_method`, NULL for COD),
  `delivery_otp` must match `^\$2[aby]\$` (bcrypt only), `delivered_at`. A fleet order can't be
  DELIVERED without a driver (CHECK).
- `order_items(order_id, product_id UNIQUE together, product_name + unit_price_npr snapshot)`.
- `ledger_accounts`: types SYSTEM_ESCROW, PLATFORM_REVENUE (singletons), GATEWAY_CLEARING (ESEWA,
  KHALTI), VENDOR_WALLET (auto-created per vendor by trigger), DRIVER_WALLET (created lazily on first
  settlement). Escrow balance ≥ 0 (CHECK).
- `ledger_transactions(kind, idempotency_key UNIQUE, order_id?)` and
  `ledger_entries(transaction_id, account_id, amount_npr <> 0)`. Postings are signed balance deltas
  that sum to 0 per journal, enforced at COMMIT by deferred constraint triggers. A journal needs ≥ 2
  postings. Postings can be added only in the transaction that created the header (checked with
  `created_at = now()`, which survives savepoints). Both tables are append-only.
- `disputes`, `reviews` (double-blind: `is_published DEFAULT false`, `published_at` consistency CHECK,
  one review per direction per order).
- Money columns are `numeric(12,2)` read as JS `number` (Drizzle `mode: 'number'`). Service
  arithmetic is done in **integer paisa** (`apps/api/src/ledger/money.ts`: `toPaisa` / `toNpr`).

### Custom PostGIS geometry type (important)

Drizzle 0.45's built-in `geometry()` **ignores `srid`**: it emits `geometry(point)` DDL and writes
SRID-less WKT `point(x y)`. The project therefore uses a custom type in
`packages/db/src/schema/columns.ts`:

```ts
export const geoPoint = customType<{ data: GeoPoint; driverData: string }>({
  dataType: () => `geometry(Point,${String(GEO_SRID)})`, // DDL: geometry(Point,4326)
  toDriver: (point) => toEwktPoint(point, GEO_SRID), // 'SRID=4326;POINT(lng lat)'
  fromDriver: (hex) => {
    // pg returns hex EWKB
    const { point, srid } = parseHexEwkbPoint(hex);
    if (srid !== GEO_SRID)
      throw new Error(`Expected SRID ${String(GEO_SRID)}, got ${String(srid)}`);
    return point;
  },
});
```

- `GeoPoint = { x: number /* longitude */, y: number /* latitude */ }` (`shared-types`
  `geoPointSchema`). **x = lng, y = lat.**
- `packages/db/src/geo/ewkb.ts`: `parseHexEwkbPoint` handles little- and big-endian input and the
  optional SRID flag, and rejects non-points, Z/M dimensions and malformed hex. `toEwktPoint` rejects
  non-finite coordinates. Unit tests pin a real PostGIS output
  (`0101000020E61000009CA223B9FC535540F38E537424B73B40` = Thamel 85.3123, 27.7154).
- PostGIS behaviour (tested): points with SRID 0 are stamped 4326 by the typmod, a different SRID
  (e.g. 3857) or a non-Point is rejected, and the generated address `location` cannot be written directly.
- Serviceability SQL (SPEC §2) as used in tests:
  `ST_DWithin(v.location::geography, customer::geography, v.radius_km * 1000 * 1.1)`.
  CITY_WIDE matches `vendors.municipality_palika_string = customer_addresses.municipality_palika_string`
  exactly. No feed/serviceability **endpoint** exists yet.

## 5. Transactional outbox and events

**Write side** (`packages/db/src/outbox.ts`):

```ts
await enqueueDomainEvent(tx, { type: 'order.placed', aggregateId: order.id, payload: {...} });
```

This validates the full envelope against `domainEventSchema` (shared-types), then inserts it into
`outbox_events(id = event_id, event_type, topic, aggregate_id, payload jsonb, occurred_at,
published_at NULL, publish_attempts, last_error)` **inside the caller's DB transaction**. The event
exists only if the business change commits. The partial index `outbox_events_unpublished_idx`
covers `(occurred_at, id) WHERE published_at IS NULL`.

**Relay** (`apps/worker/src/outbox/outbox-relay.ts`, class `OutboxRelay`):

- Each batch runs in one transaction: `SELECT … WHERE published_at IS NULL AND publish_attempts < 20
ORDER BY occurred_at, id LIMIT 100 FOR UPDATE SKIP LOCKED`. Replicas never publish the same row.
- Each row is rebuilt with `outboxRowToDomainEvent` and re-validated. A malformed row gets
  `publish_attempts+1` and `last_error` set, and is skipped without blocking valid rows. It is
  dead-lettered in place after 20 attempts.
- Publishing uses `DomainEventPublisher.publish()` (`packages/kafka/src/producer.ts`) →
  `producer.sendBatch`, grouped by topic, **key = aggregate_id**, headers
  `event_id/event_type/event_version`. Only after Kafka acks is `published_at = now()` set. On
  failure the rows keep `published_at NULL` and record the error, so the next poll retries them.
- Polls every 250 ms and drains back-to-back while batches are full. Delivery is
  **at-least-once**: consumers must dedupe on `event_id`.
- Producer: `@confluentinc/kafka-javascript` KafkaJS-compatible API, created with
  `{ 'enable.idempotence': true, acks: -1 }` (`IDEMPOTENT_PRODUCER_CONFIG`).

**Events** (`shared-types/src/events/domain-events.ts`). The envelope is
`{ event_id, event_type, event_version: 1, occurred_at (ISO), aggregate_id, payload }`.

| event_type       | topic            | emitted by                                       | aggregate                  |
| ---------------- | ---------------- | ------------------------------------------------ | -------------------------- |
| `order.locked`   | order.lifecycle  | checkout (same tx as order insert)               | reservation_id             |
| `order.placed`   | order.lifecycle  | lock claim (same tx as stock decrement + PLACED) | order_id                   |
| `ledger.mutated` | ledger.mutations | every posted journal (same tx)                   | order_id ?? transaction_id |

`apps/worker/src/consumers/index.ts` registers **no** consumers yet.

## 6. Concurrency, ledger, timers (backend reference)

- **Redis 600 s lock** (`apps/api/src/inventory/inventory-lock-service.ts`). Keys are
  `inv:{vendorId}:res:{reservationId}` (JSON, `PX 600000`) and `inv:{vendorId}:holds:{productId}`
  (hash reservation→qty). The `{vendorId}` hash tag keeps them cluster-safe. Available stock =
  Postgres stock − live holds. Each attempt runs WATCH → read → MULTI/EXEC with retry, on a
  dedicated pooled connection (`apps/api/src/infra/redis-pool.ts`), because WATCH is per-connection.
  Mutation-tested: without WATCH, 20 of 10 units were granted.
- **Claim** (`checkout/checkout-service.ts#claim`): order `FOR UPDATE`, stock decrement guarded by
  `stock_quantity >= qty`, state → PLACED, `order.placed`, then the Redis lock is released after commit.
- **Settlement** (`ledger/settlement-plan.ts` is pure; `settlement-service.ts`). Capture moves money
  GATEWAY_CLEARING → SYSTEM_ESCROW. Settlement is allowed only in state DELIVERED: the vendor gets
  S − C, the commission C goes to revenue, and the delivery fee goes to the deliverer (vendor on
  SELF_DELIVERY, driver on fleet). COD self-delivery debits C from the vendor wallet (which may
  suspend it). COD fleet debits the driver the cash they collected. Idempotency keys:
  `payment-capture:<order>` and `order-settlement:<order>`.
- **BullMQ** (`apps/worker/src/queues/`). Queues `vendor-acceptance-timeout` (90 s, jobId = order_id),
  `ghost-customer-timer` (8 min, jobId = order_id), and `midnight-maintenance` (cron `0 0 * * *`,
  tz `Asia/Kathmandu`, task SUBSCRIPTION_DOWNGRADE). Handlers are **placeholders that log**
  (`pendingImplementationHandlers`). The schedule/cancel helpers live in the worker; the API does not
  enqueue timers yet.

## 7. eSewa ePay v2: signature and float-parsing rules

Code: `apps/api/src/payments/esewa/signature.ts` (pure) and `esewa-service.ts`.

1. **Message format.** SPEC's `"total_amount,transaction_uuid,product_code"` is the
   `signed_field_names` list. eSewa signs **`name=value` pairs in that order, joined by commas**:
   `total_amount=110,transaction_uuid=241028,product_code=EPAYTEST`.
2. **Signature** = `Base64(HMAC-SHA256(message, secret))`, standard Base64 (not hex, not base64url),
   44 characters.
3. **Pinned vectors** (unit tests, UAT secret `8gBm/:&EnhH.1/q`):
   - request `total_amount=110,transaction_uuid=241028,product_code=EPAYTEST` →
     `i94zsd3oXF6ZsSr/kGqT4sSzYQzjj1W/waxjWyRwaME=`
   - documented success callback (`transaction_code=000AWEO,status=COMPLETE,total_amount=1000.0,
transaction_uuid=250610-162413,product_code=EPAYTEST,signed_field_names=…`) →
     `62GcfZTmVkzhtUeh+QJ1AqiJrjoWWGof3U+eTPTZ7fA=`
4. **Float parsing rule (critical).** The callback `data` is base64 JSON in which `total_amount` is a
   JSON _number literal_ such as `1000.0`, and the signature covers that exact text. A plain
   `JSON.parse` yields `1000`, so a re-signed message would say `total_amount=1000` and verification
   fails. `decodeEsewaCallback` uses a `JSON.parse` reviver with `context.source` (Node ≥ 21) to keep
   every number as its **source string**. Never round-trip callback numbers through `Number` before
   verifying.
5. **Callback verification.** It recomputes over the callback's own `signed_field_names`, which must
   include `status, total_amount, transaction_uuid, product_code, signed_field_names`. The comparison
   is constant-time (`timingSafeEqual`), and `product_code` must equal the configured code.
6. **Amount check.** Only after verification is `total_amount` parsed
   (`Number(s.replaceAll(',', ''))`, then `Math.round(×100)` to paisa). It is compared to the order
   snapshot `subtotal + delivery_fee` with a **±1 paisa (±0.01 NPR)** tolerance, under
   `SELECT … FOR UPDATE`.
7. **Request form.** Amount strings are produced by `formatNpr(paisa) = String(paisa / 100)`: no
   trailing zeros, no grouping ("1050", "1050.5"). Fields: `amount, tax_amount "0",
product_service_charge "0", product_delivery_charge, total_amount, transaction_uuid,
product_code, success_url, failure_url, signed_field_names, signature`. A fresh `randomUUID()`
   `transaction_uuid` is generated per initiate and stored as `orders.payment_gateway_ref`.
8. Only status `COMPLETE` credits. Other statuses return `{ status, payment: null }` with no mutation.

**Khalti** (`payments/khalti/`): `POST {KHALTI_BASE_URL}/epayment/initiate/` with header
`Authorization: Key <secret>` and `amount` in **integer paisa**; the `pidx` is stored as
`payment_gateway_ref`. `POST …/epayment/lookup/ {pidx}` credits only when `status === 'Completed'`
and `total_amount` (paisa) is within ±1 of the snapshot. SPEC's base URL `https://a.khalti.com/api/v2`
is production; the sandbox is `https://dev.khalti.com/api/v2`.

**Shared confirmation tail** (`payments/payment-confirmation.ts`): one transaction locks the order by
`(payment_method, payment_gateway_ref)` `FOR UPDATE`, checks the amount, and captures escrow once.
After commit it claims the lock, and the order becomes PLACED. If the lock expired or stock vanished,
the order becomes **FAILED**, stays PAID with money in escrow, and the response is
`409 PAID_AFTER_SESSION_EXPIRED` with `refund_required: true` (no refund flow exists yet).
Mutation-tested: without `FOR UPDATE`, all 6 concurrent callbacks reported a first credit.

The controllers (`apps/api/src/routes/cart.ts`, `payments.ts`) import the types from there.
`apps/api/src/routes/views.ts` now only holds the domain→view mapper functions. The API integration
tests parse **every** response body through these schemas (`test/support/http.ts#bodyOf(schema,
res)`), so a server change that breaks the contract fails the suite. The mobile app can use the same
schemas to validate responses at runtime.

**Checkout behaviour.**

- Pricing is done on the server from DB prices, and client prices are never trusted.
  Delivery fee = vendor base fee. Commission = subtotal × rate in basis points, rounded half-up to
  the paisa (0 on SUBSCRIPTION).
- The vendor must be LIVE. A subtotal below the vendor's MOV → 422 (the SPEC surcharge amount is
  undefined, so no surcharge is applied). COD is refused if the customer's average published
  VENDOR_TO_CUSTOMER rating is below 3.0.
- The service creates a 4-digit CSPRNG delivery OTP and stores only its bcrypt hash. It locks
  inventory, then inserts the order, items and `order.locked` in one transaction. Duplicate
  submissions with the same idempotency key are serialised with a Redis mutex
  (`apps/api/src/infra/redis-mutex.ts`) and replays return the same order. **A replay rotates the OTP**, so only
  the newest `delivery_otp` is valid.
- COD orders are claimed immediately (PLACED). Prepaid orders stay PENDING_PAYMENT until the gateway
  confirms within the 600 s lock.

**Error envelope** `{ error: { code, message, details? } }`. The contract is `errorBodySchema` / `ErrorBody`
in `packages/shared-types/src/api/responses.ts`, emitted by the handler in `apps/api/src/http/errors.ts`.
Clients branch on `code` (the `message` is for logs); `details` depends on the code:

| HTTP            | codes                                                                                                                                                                                                                                                                                                                            |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400             | `VALIDATION_FAILED` (details.issues[{path,message}]), `MALFORMED_REQUEST`, `INVALID_CART`, `INVALID_PAYMENT_CALLBACK`                                                                                                                                                                                                            |
| 401 / 403       | `UNAUTHENTICATED` / `FORBIDDEN`                                                                                                                                                                                                                                                                                                  |
| 404             | `NOT_FOUND`, `ORDER_NOT_FOUND`, `PAYMENT_NOT_FOUND`                                                                                                                                                                                                                                                                              |
| 409             | `INSUFFICIENT_STOCK` (details.shortfalls[{productId, requested, available}]), `IDEMPOTENCY_KEY_REUSED`, `WRONG_PAYMENT_METHOD`, `ORDER_NOT_PAYABLE`, `ORDER_STATE_CONFLICT`, `CHECKOUT_IN_PROGRESS`, `PAYMENT_AMOUNT_MISMATCH` (details.expected_npr/paid_npr), `PAID_AFTER_SESSION_EXPIRED` (details.order_id, refund_required) |
| 410             | `RESERVATION_EXPIRED` (the SPEC "Session Expired": return the user to the cart)                                                                                                                                                                                                                                                  |
| 422             | `VENDOR_UNAVAILABLE`, `PRODUCT_UNAVAILABLE` (details.product_ids), `BELOW_MINIMUM_ORDER_VALUE` (details.minimum_npr/subtotal_npr), `COD_NOT_AVAILABLE`                                                                                                                                                                           |
| 502 / 503 / 500 | `PAYMENT_GATEWAY_ERROR` / `CHECKOUT_BUSY` / `INTERNAL_SERVER_ERROR`                                                                                                                                                                                                                                                              |

### Auth contract (`apps/api/src/auth/access-token.ts`, `http/auth.ts`)

- HS256 only (`alg: none` and other algorithms are rejected). Issuer `hamro-pasal-api`, audience
  `hamro-pasal-app`, TTL 900 s. Claims `{ sub: user uuid, role: UserRole }`. Header
  `Authorization: Bearer <jwt>`.
- **Not implemented:** OTP login, token issuance endpoint, refresh tokens (SPEC: 7-day HTTP-only
  refresh; access token in memory; MMKV with encryption only if persistence is needed). Adding
  `POST /api/auth/otp/*` is backend scope and must be requested explicitly.
- **Dev tokens:** `apps/api/scripts/mint-dev-token.ts` signs a real 15-minute access token (same
  `signAccessToken` the API verifies with) for a **seeded** user, looked up by phone in the dev DB,
  using `JWT_ACCESS_SECRET` and `DATABASE_URL` from the root `.env`. It refuses to run with
  `NODE_ENV=production`. The token alone goes to stdout; details go to stderr.

  ```
  pnpm --filter @hamro-pasal/api token:dev                                 # +9779800000001 Aarav, CUSTOMER
  pnpm --filter @hamro-pasal/api token:dev -- --phone 9800000011           # Thamel Kirana Pasal, VENDOR
  TOKEN=$(pnpm --silent --filter @hamro-pasal/api token:dev)               # capture for curl / the app
  ```

  Cart and payment routes are CUSTOMER-only: a VENDOR/DRIVER token gets 403 there. Tokens expire
  after 15 minutes, so re-run the script. Covered by `apps/api/test/mint-dev-token.int.test.ts`, and
  verified live against the dev DB (no token → 401, CUSTOMER token → route response, VENDOR → 403).

### Not implemented (backend)

No routes for: auth, catalog/vendor feed (geospatial serviceability), addresses (the schema exists in
shared-types), releasing a lock early, order tracking/state transitions (Preparing → Out for
Delivery → Arrived), 60 s cancellation window, delivery OTP verification, reviews, disputes,
Socket.io `/orders` and `/chat`, push notifications, refunds, admin, `/metrics`, rate limiting. SMS
adapters exist (`apps/api/src/sms/sms-gateway.ts`: Sparrow, Aakash, Mock; strict +977) but no route
uses them.

## 9. Localization utilities (shared-types, usable from mobile)

- `toNepaliNumerals(num)` (`localization/numerals.ts`) returns Devanagari digits (e.g. 1250.5 →
  `१२५०.५`) with no grouping and no exponent notation, and throws on NaN/Infinity. It uses
  `toLocaleString('en-US', {useGrouping:false, maximumFractionDigits:20})`, so it needs `Intl` on
  Hermes (available on RN 0.86). Verify on device.
- `NEPAL_PHONE_REGEX` `^\+9779[0-9]{9}$`, `normalizeNepalPhone(input)` (accepts `98…`, `+977…`,
  `977…` (13 digits), `00977…`, and separators), `isNepalPhone`.
- `nepalAddressInputSchema`: province_id 1–7; district must belong to that province (all 77
  districts plus aliases such as "Kavre" → "Kavrepalanchok", canonicalised); palika, tole and landmark
  non-blank (≤ 120 chars); ward 1–33; pin inside Nepal's bounding box (lat 26.3–30.5, lng
  80.0–88.25); strict object, so a `zip_code` field is rejected. The Palika list (753) is not bundled.
- `NEPAL_PROVINCES`, `NEPAL_DISTRICTS_BY_PROVINCE`, `lookupNepalDistrict` for pickers.
- `INVENTORY_LOCK_TTL_SECONDS = 600`, `COD_MIN_CUSTOMER_RATING = 3.0`,
  `VENDOR_WALLET_HARD_FLOOR_NPR = -2000`.

**Integration notes for the mobile agent**

- Import contracts from `@hamro-pasal/shared-types`: request schemas (`src/api/requests.ts`),
  **response schemas and types** (`src/api/responses.ts`), entities, enums, localization. It depends
  only on `zod`, so it is safe for React Native. It resolves via `dist/`, so build it first. Non-2xx
  bodies match `errorBodySchema` (`ErrorBody`) from the same module; see the code table in §8.
- Authenticate during development with `token:dev` (§8). Pass the token as
  `Authorization: Bearer <token>`. Keep it in memory, per SPEC.
- **Checkout replays:** `reservation.id` is `null` when the replayed order has no lock (it no longer
  returns an empty string).
- **Checkout flow.** Generate one `idempotency_key` per checkout attempt and reuse it on retries.
  Keep only the **latest** `delivery_otp` (replays rotate it). Show the 600 s countdown from
  `reservation.expires_at`. On reconnect, call `GET /api/cart/lock-status?order_id=`: `ACTIVE`
  resumes, `EXPIRED` purges the cart and shows "Session Expired", `RELEASED` means the order has left
  checkout. SPEC edge case 4 (single-vendor cart) must be enforced in the Zustand cart store. The API
  also takes exactly one `vendor_id`.
- **eSewa.** Call `POST /api/payments/esewa/initiate`, then auto-submit an HTML form with the
  returned `fields` to `payment_url` in a WebView (SPEC: prefer an App-to-App intent if the eSewa app
  is installed). Intercept navigation to `ESEWA_SUCCESS_URL`, read the `data` query param **verbatim**
  (do not decode or re-encode it), and `POST /api/payments/esewa/webhook {data}`. Intercept
  `failure_url` to treat the attempt as cancelled.
- **Khalti.** Call `POST /api/payments/khalti/initiate`, open `payment_url` (WebBrowser). On return to
  `KHALTI_RETURN_URL`, take `pidx` and `POST /api/payments/khalti/lookup {pidx}`. `payment: null`
  means not completed yet (e.g. `Pending`/`Initiated`), so poll or let the user retry.
- Handle `409 PAID_AFTER_SESSION_EXPIRED` explicitly (the customer paid but the order failed, and a
  refund is needed) and `409 CHECKOUT_IN_PROGRESS` (retry shortly).
- The tenant rule (SPEC §1) is still client-side work: +977 only; if the GPS country ≠ NP, block the
  app, clear the cache, and show the blocking modal "Service Unvailable in your territory" (SPEC
  spelling).

## 11. Decisions made (with the user's approval, where one was asked)

- Express 5 (not NestJS) for the API; BullMQ **and** Kafka for background work (user choices, P0).
- Wallet invariant: conditional CHECK plus a BEFORE trigger. Limit in `platform_settings`.
  Double-entry replaced the single-entry wallet ledger (user choices, P2/P3).
- Settlement: delivery fee to the deliverer. Transactional outbox for events (user choices, P3).
- Checkout creates the order together with the lock. JWT verification now, login later (user
  choices, P4).
- Enums are stored as strings (SPEC shows numeric TS enums). `vendors.fulfillment_mode` was added
  (implied by SPEC §2). `orders.reservation_id` was added.
- ioredis 5.x (not 6), because `ioredis-mock` requires it.

## 12. Known gaps and risks

- API boot is blocked until `SPARROW_SMS_TOKEN` / `SPARROW_SMS_FROM` are set in `.env`, or
  `SMS_PROVIDER` is changed (see §3).
- A lock that expires mid-claim is guarded by the Postgres stock check, but the customer may have
  paid (the order becomes FAILED and needs a refund, which is not implemented).
- The `order.locked` outbox write can't be atomic with Redis. The lock is released if the insert fails.
- Hot rows: every settlement locks the single SYSTEM_ESCROW and PLATFORM_REVENUE accounts.
- Tightening the wallet limit does not retroactively suspend vendors until their next posting.
- Sparrow/Aakash payloads use +977 per SPEC; the providers may expect the 10-digit national format,
  which needs verifying in their sandboxes. No live eSewa or Khalti calls have been made (tests fake
  the gateway HTTP).
- The small-cart surcharge amount is undefined in SPEC; carts below MOV are rejected instead.
- One parallel integration run hung once in Phase 3 and could not be reproduced afterwards.
- The Prometheus target stays down until `/metrics` exists.
