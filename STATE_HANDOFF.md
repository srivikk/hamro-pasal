### Tables and key invariants

- `users(phone UNIQUE CHECK ~ '^\+9779[0-9]{9}$', role, first_name, last_name?)`.
- `customer_addresses`: Nepal hierarchy + `exact_lat/exact_lng` (double) + generated `location`
  `ST_SetSRID(ST_MakePoint(exact_lng, exact_lat), 4326)` with GiST. Province 1–7, ward ≥ 1.
  **No route writes it yet** (§11).
- `vendors`: SPEC Vendor fields + `user_id`, `business_name`, `base_delivery_fee_npr`,
  `scheduled_downgrade`, `fulfillment_mode` ∈ {SELF_DELIVERY, PLATFORM_FLEET}. `pricing_model` is
  nullable until LIVE; SUBSCRIPTION ⇒ commission 0 (CHECKs). `location geometry(Point,4326)` with two
  GiST indexes (geometry, and `(location::geography)` for metre-accurate `ST_DWithin`). Wallet floor
  `CHECK (wallet_balance_npr >= -2000 OR status = 'SUSPENDED')` + trigger `enforce_vendor_wallet_limit`
  (suspends strictly below `platform_settings.vendor_wallet_suspension_limit_npr`, configurable in
  [-2000, 0]). `wallet_balance_npr` is a **projection**: only ledger postings may change it.
- `products(vendor_id, name UNIQUE per vendor, price_npr > 0, stock_quantity >= 0, is_active)`.
- `orders`: SPEC OrderSnapshot + `idempotency_key UNIQUE`, `reservation_id UNIQUE`, `driver_user_id`,
  `payment_gateway_ref` (UNIQUE per method, NULL for COD), bcrypt-only `delivery_otp`,
  **`delivered_at`** (exists in the DB, **not exposed by `OrderView`**, §11). A fleet order can't be
  DELIVERED without a driver (CHECK).
- `order_items(order_id, product_id UNIQUE together, product_name + unit_price_npr snapshot)`.
- Ledger: `ledger_accounts` (SYSTEM_ESCROW, PLATFORM_REVENUE, GATEWAY_CLEARING ESEWA/KHALTI,
  VENDOR_WALLET auto-created per vendor, DRIVER_WALLET lazily), `ledger_transactions(kind,
idempotency_key UNIQUE, order_id?)`, `ledger_entries(amount_npr <> 0)`. Journals balance to 0 at
  COMMIT (deferred triggers), need ≥ 2 postings, can only be posted in the creating transaction, and
  are append-only. Escrow balance ≥ 0.
- `disputes(order_id, opened_by_user_id, reason, status, resolved_by_user_id?, resolved_at?)` and
  `reviews(order_id, direction CUSTOMER_TO_VENDOR|VENDOR_TO_CUSTOMER, rating 1–5, comment?,
is_published DEFAULT false, published_at, one per direction per order)`. **Tables exist, no routes.**
- Money is `numeric(12,2)` read as JS `number`. Services compute in integer paisa
  (`apps/api/src/ledger/money.ts`). The mobile app does the same (`src/lib/money.ts`).

### Schema ↔ Zod contract

`packages/db/src/schema/contract.ts` asserts at **compile time** that every table's `$inferSelect`
equals the strict Zod type in `shared-types/src/domain/entities.ts`; `test/contract.int.test.ts`
parses real rows at runtime. A column change must update both sides or `tsc` fails.

### Custom PostGIS geometry

`packages/db/src/schema/columns.ts#geoPoint` writes EWKT `SRID=4326;POINT(lng lat)` and reads hex
EWKB (`geo/ewkb.ts`), because Drizzle 0.45's built-in `geometry()` ignores `srid`.
**`GeoPoint = { x: longitude, y: latitude }`.** Serviceability SQL (SPEC §2, used in tests):
`ST_DWithin(v.location::geography, customer::geography, v.radius_km * 1000 * 1.1)`; CITY_WIDE compares
`municipality_palika_string` exactly. **No feed endpoint exists** (§11).

## 5. Transactional outbox and events

- Write side: `enqueueDomainEvent(tx, { type, aggregateId, payload })` (`packages/db/src/outbox.ts`)
  validates against `domainEventSchema` and inserts into `outbox_events` **inside the caller's
  transaction**.
- Relay: `apps/worker/src/outbox/outbox-relay.ts#OutboxRelay`, batches of 100
  `FOR UPDATE SKIP LOCKED`, polls every 250 ms, publishes with `DomainEventPublisher` (key =
  aggregate_id, headers event_id/type/version), sets `published_at` only after the Kafka ack, and
  dead-letters after 20 attempts. At-least-once: consumers must dedupe on `event_id`.
- Producer: `@confluentinc/kafka-javascript`, `{ 'enable.idempotence': true, acks: -1 }`.
- Events: `order.locked` (checkout, aggregate reservation_id), `order.placed` (lock claim, order_id),
  `ledger.mutated` (every journal). `apps/worker/src/consumers/index.ts` registers **no** consumers.

## 6. Concurrency, ledger, timers

- Redis 600 s lock (`apps/api/src/inventory/inventory-lock-service.ts`): keys
  `inv:{vendorId}:res:{reservationId}` (JSON, `PX 600000`) and `inv:{vendorId}:holds:{productId}`.
  WATCH → read → MULTI/EXEC with retries on a dedicated pooled connection. Available = Postgres stock
  − live holds.
- Claim (`checkout/checkout-service.ts#claim`): order `FOR UPDATE`, stock decrement guarded by
  `stock_quantity >= qty`, state → PLACED, `order.placed`, lock released after commit.
- Settlement (`ledger/settlement-plan.ts` pure, `settlement-service.ts`): capture moves money
  GATEWAY_CLEARING → SYSTEM_ESCROW. Settlement happens only in DELIVERED; the vendor gets S − C, C goes
  to revenue, and the delivery fee goes to the deliverer. COD self-delivery debits C from the vendor
  wallet (may suspend); COD fleet debits the driver. Keys `payment-capture:<order>`,
  `order-settlement:<order>`. **Nothing triggers settlement yet** (no DELIVERED transition route).
- BullMQ (`apps/worker/src/queues/`): `vendor-acceptance-timeout` (90 s), `ghost-customer-timer`
  (8 min), `midnight-maintenance` (cron `0 0 * * *`, Asia/Kathmandu). Handlers are **placeholders
  that log**; the API does not enqueue any timer yet.

## 7. eSewa ePay v2 and Khalti rules (backend)

Code: `apps/api/src/payments/esewa/{signature,esewa-service}.ts`, `payments/khalti/*`.

1. The signed message is `name=value` pairs in `signed_field_names` order, comma-joined:
   `total_amount=110,transaction_uuid=241028,product_code=EPAYTEST`.
2. Signature = standard Base64 of HMAC-SHA256 (44 chars). Pinned vectors (UAT secret
   `8gBm/:&EnhH.1/q`): request above → `i94zsd3oXF6ZsSr/kGqT4sSzYQzjj1W/waxjWyRwaME=`; documented
   success callback → `62GcfZTmVkzhtUeh+QJ1AqiJrjoWWGof3U+eTPTZ7fA=`.
3. **Float rule:** the callback `data` is base64 JSON whose `total_amount` is a number literal such as
   `1000.0`; `decodeEsewaCallback` keeps every number as its **source string** (JSON.parse reviver
   with `context.source`). Never round-trip callback numbers through `Number` before verifying.
4. Verification recomputes over the callback's own `signed_field_names` (must include status,
   total_amount, transaction_uuid, product_code, signed_field_names), compares in constant time,
   checks product_code, and only then compares the amount to `subtotal + delivery_fee` (±1 paisa)
   under `SELECT … FOR UPDATE`. Only `COMPLETE` credits.
5. Initiate returns `{ payment_url, method: 'POST', fields }`, where `fields` includes
   `success_url` and `failure_url` (from `ESEWA_SUCCESS_URL` / `ESEWA_FAILURE_URL`). A fresh
   `transaction_uuid` per initiate is stored as `payment_gateway_ref`.
6. Khalti: `POST {KHALTI_BASE_URL}/epayment/initiate/` (`Authorization: Key <secret>`, amount in paisa),
   `pidx` stored as `payment_gateway_ref`; `lookup` credits only on `Completed` within ±1 paisa.
   SPEC's `https://a.khalti.com/api/v2` is production; sandbox is `https://dev.khalti.com/api/v2`.
7. Shared tail (`payments/payment-confirmation.ts`): lock order by `(payment_method,
payment_gateway_ref)` `FOR UPDATE`, capture escrow once, then claim the lock → PLACED. If the lock
   expired or stock vanished: order **FAILED**, stays PAID, response `409 PAID_AFTER_SESSION_EXPIRED`
   `{ order_id, refund_required: true }`. **No refund flow exists.**
8. **The API has no handlers at `ESEWA_SUCCESS_URL` / `ESEWA_FAILURE_URL` / `KHALTI_RETURN_URL`.** The
   mobile WebView intercepts those navigations (§9.5), so it works without them, but a browser
   fallback or the SPEC's eSewa app-to-app intent would need real landing pages.

delivery_fee_npr, total_npr, created_at}` (no OTP hash, gateway ref, commission or `delivered_at`).

**Checkout behaviour:** server-side pricing from DB (client prices never trusted); delivery fee =
vendor base fee; commission half-up to the paisa (0 on SUBSCRIPTION). Vendor must be LIVE (else
`422 VENDOR_UNAVAILABLE`); below MOV → `422 BELOW_MINIMUM_ORDER_VALUE` (no surcharge: amount undefined
in SPEC); COD refused below average published VENDOR_TO_CUSTOMER rating 3.0. Creates a CSPRNG 4-digit
OTP (bcrypt stored), locks inventory, inserts order + items + `order.locked` in one transaction.
Same idempotency key → Redis-mutex-serialised replay of the same order, **rotating the OTP**. COD is
claimed immediately (PLACED); prepaid stays PENDING_PAYMENT until the gateway confirms within 600 s.
Lock-status returns RELEASED for any order no longer in PENDING_PAYMENT.

**Error envelope** `{ error: { code, message, details? } }` (`errorBodySchema`, emitted by
`http/errors.ts`). Clients branch on `code`:

**Auth** (`auth/access-token.ts`, `http/auth.ts`): HS256 only, issuer `hamro-pasal-api`, audience

### 9.3 API client (`src/api/http.ts`)

`apiRequest({ method, path, query?, body?, schema })` reads the access token from `useAuthStore` **at
call time** (`Authorization: Bearer`), JSON-encodes the body, builds the query string by hand (RN's
`URLSearchParams` is incomplete), parses non-2xx bodies with `errorBodySchema` into
`ApiError(status, code, message, details)`, and validates 2xx bodies with the given shared-types
schema. Client-side codes: `NOT_SIGNED_IN` (no request sent), `NETWORK_ERROR`, `UNEXPECTED_RESPONSE`.
`API_URL` comes from `src/config/api.ts`, which throws a descriptive startup error if
`EXPO_PUBLIC_API_URL` is missing or malformed. Query defaults (`query-client.ts`): staleTime 30 s,
3 retries with capped exponential backoff, **mutations never retried automatically**.

### 9.4 Checkout and lock status

- `useCheckout` (`src/api/mutations.ts`) builds `checkoutRequestSchema` from the cart (ids and
  quantities only), refuses to send an invalid cart (`INVALID_CART`), stores the OTP, then
  `startSession`. `RESERVATION_EXPIRED` → `expireSession`; `IDEMPOTENCY_KEY_REUSED` → new key next time.
- The cart (`app/(tabs)/cart.tsx`) requires: subtotal ≥ MOV, **a saved delivery address**, and a
  payment method (eSewa / Khalti / COD). Summary rows: subtotal, delivery fee, platform fee (**Rs. 0**:
  SPEC §4 deducts commission from the vendor, and the API charges subtotal + delivery fee), total. The
  cart is frozen while a reservation is pending.
- `useLockStatus` (`src/api/queries.ts`) polls `GET /api/cart/lock-status` every **5 s**, only while
  `selectShouldPollLock`, continuing through network errors (SPEC edge case 1). Mounted once by
  `src/features/checkout/CheckoutSessionWatcher.tsx`, which also watches for any transition to
  PLACED (COD at checkout, payment confirmation or poll), records `placedAt` and
  `router.push('/order/[id]')` (**only the id travels in the route; never the OTP**).

### 9.5 Payment WebView interception (`src/features/payment/`, `src/components/PaymentWebViewModal.tsx`)

- A successful prepaid checkout calls `usePaymentFlow().start(orderId, method)` automatically. The
  reservation panel also has a "Pay with …" retry button.
- **eSewa:** `POST /api/payments/esewa/initiate` → `buildEsewaFormHtml(payment_url, fields)` builds an
  auto-submitting POST form (every value HTML-escaped; `payment_url` must be http(s)) → WebView
  `source={{ html }}`.
- **Khalti:** `POST /api/payments/khalti/initiate` → WebView `source={{ uri: payment_url }}`.
- `onNavigationStateChange` → `interpretNavigation(target, url)` (`payment-redirect.ts`):
  - eSewa success and failure are matched on **origin + path equality** with the signed
    `fields.success_url` / `failure_url` (never substring).
  - eSewa `data` is extracted by `rawQueryParam`, percent-decoded once and **never via
    URLSearchParams**, which would turn `+` into a space and break the signature.
  - The Khalti return is any page **outside Khalti's own origin** that carries this payment's `pidx`
    (the return_url is server config, not sent to the app).
- Only the first callback per attempt is acted on (a ref guard). Each attempt is a fresh keyed
  session. The WebView runs `incognito` with `setSupportMultipleWindows={false}`.
- **The server only learns of a payment because the app forwards it:** eSewa success →
  `POST /esewa/webhook {data}`; Khalti `Completed`/`Pending`/no status → `POST /khalti/lookup {pidx}`;
  other Khalti statuses, eSewa failure_url or Cancel → failure toast, reservation kept. Results:
  `payment` present → `applyPaymentView` (PLACED clears the cart and opens tracking); `null` →
  "not complete" toast; `409 PAID_AFTER_SESSION_EXPIRED` → order FAILED + refund toast;
  `RESERVATION_EXPIRED` → Session Expired. `useLockStatus` keeps polling as a safety net.
- **Not implemented:** SPEC's eSewa App-to-App intent; the WebView is the only path.

### 9.6 Order tracking and the 60-second cancellation (`app/order/[id]/index.tsx`, `src/features/order/`)

- The order is read with `fetchOrder` (`src/api/orders.ts`), which **uses `GET /api/cart/lock-status`
  because no order endpoint exists**, refreshed every 30 s until terminal (stand-in for the Socket.io
  `/orders` namespace).
- **Cancellation window:** `CANCELLATION_WINDOW_MS = 60_000` from the persisted `placedAt`, clamped to
  [0, 60 s] (cannot be restarted or stretched by clock changes), with a live countdown and a "Cancel
  Order" button. When it closes, a still-PLACED order is **displayed** as PREPARING
  (`displayedOrderState`; the stored state is untouched).
- **Cancellation is a MOCK:** `src/features/order/mock-cancel-api.ts#cancelOrder(orderId, placedAtMs)`
  waits 300 ms and rejects with `CANCELLATION_WINDOW_CLOSED` after 60 s. On success the app marks the
  order CANCELED **locally only** (order store, checkout session), erases the OTP and shows a toast.
  **The server order stays PLACED, the vendor still gets it, and prepaid money is not refunded.**
  Because tracking stops polling terminal orders, the local CANCELED is not overwritten.
- Tracker: Order Placed → Preparing → Out for Delivery → Arrived → Delivered with

### 9.10 Dispute chat + privacy-filtered Socket.io scaffold

- **Socket client** (`src/services/socket.ts`):
  - `createChatSocket()` → `io(\`${API_URL}/chat\`, …)`with`transports: ['websocket']`,
`autoConnect: false` and infinite reconnection.
  - **Backoff 1 s → 2 s → 4 s → 8 s → 16 s → 30 s cap** (`randomizationFactor: 0`; verified against
    the real Manager in tests).
  - `auth` callback sends `{ token }` from `useAuthStore` at every (re)connect.
  - Heartbeat: **`HEARTBEAT_INTERVAL_MS = 25_000` must be set as the server's `pingInterval`**. In
    Socket.io the client cannot set it; 25 000 is also the default.
- **Typed events:**
  - client → server: `chat:join { order_id }`, re-sent on every reconnect;
  - both directions: `chat:new_message (ChatMessage, ack)`, where the client expects an ack within
    10 s, else the message shows "Not sent. Tap to retry.".
- **Wire contract and privacy filter** (`src/features/dispute/chat-contract.ts`):
  - `ChatMessage = { id, client_id|null, order_id, sender: ChatUser, body ≤ 2000, attachments ≤ 4 [{
url (https), content_type image/* }], sent_at ISO }`.
  - `ChatUser = { id, first_name|null, role }` is an **allowlist** (`z.object` strips every other
    key), so `last_name`, `phone_number`/`phone`, email or any future field is removed from **every
    incoming payload before rendering and every outgoing payload before emitting**. Invalid payloads
    are dropped.
  - Bubbles show the first name, the role label when there's no name, or "You".
  - SPEC implicit requirement 6 still requires the **server** to strip these fields before
    broadcasting; the client filter is defence in depth.
- **Screen:** `app/order/[id]/dispute.tsx` uses `useDisputeChat` (optimistic send, server echo
  reconciled by `client_id`, reconnect banner). It is only open inside the 48 h window. The own user
  is derived from JWT claims (`sub`, `role`; `first_name` null).
- **Evidence upload is a MOCK:** `mock-evidence-upload.ts` validates image type and ≤ 10 MB, then
  returns a fake `https://evidence.hamropasal.test/...webp` URL. There is no compression
  (react-native-compressor is not installed), no presigned R2 URL and no upload.
- **There is no chat server:** on a device the socket keeps retrying.

## 12. Decisions made (with the user's approval where one was asked)

- Express 5 (not NestJS); BullMQ **and** Kafka; conditional wallet CHECK + trigger with limit in
  `platform_settings`; double-entry ledger; delivery fee to the deliverer; transactional outbox;
  checkout creates the order together with the lock; JWT verification now, login later; enums
  stored as strings; ioredis 5.x (ioredis-mock needs it).
- Mobile: access token memory-only, refresh token and locale in AES-256 MMKV (key in the keychain);
  cart in plain MMKV; single-vendor enforcement in the store with a replace prompt; customer platform
  fee shown as Rs. 0; payment-method picker in the cart (the API needs it at checkout); payment
  callbacks forwarded to the webhook/lookup endpoints (polling alone never confirms a payment); the
  delivery OTP persisted in encrypted storage (it was memory-only until Phase 5.5) and never passed
  through route params; mocks for every missing endpoint behind a single file each; geofence = box +
  reverse geocoder with a box fallback.

## 13. Known gaps and risks

- **No live end-to-end run** of the app against the API, and no live eSewa/Khalti sandbox session.
  All gateway and API behaviour on mobile is verified with msw. The first sandbox run should confirm
  that eSewa's real success redirect carries `data` in the form `rawQueryParam` expects.
- **Mocked cancellation diverges from the server** (see §9.6). Do not ship it.
- **Paid-but-failed orders** (`PAID_AFTER_SESSION_EXPIRED`) have no refund path.
- The `order.locked` outbox write can't be atomic with Redis (the lock is released if the insert fails).
- Hot rows: every settlement locks the single SYSTEM_ESCROW and PLATFORM_REVENUE accounts.
- Tightening the wallet limit does not retroactively suspend vendors until their next posting.
- Sparrow/Aakash payloads use +977 per SPEC; the providers may expect the 10-digit national format.
- The small-cart surcharge amount is undefined in SPEC; carts below MOV are rejected.
- **Bounding boxes:** the address pin check uses shared-types' slightly wider Nepal box, while the
  territory gate uses the exact extreme points. A pin within about 5 km of the border can pass one
  and fail the other.
- **Push notifications, Sentry, OTA updates and the Mapbox pin-drop** are not started.
